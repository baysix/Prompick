# 서버 운영 (Lightsail)

프론트·백엔드·리버스 프록시가 서울 리전 한 대 안에 도커로 산다. DB와 저장소는 Supabase.

- 주소: https://yspace.kr
- 서버: Lightsail 4GB / 2vCPU, 서울(ap-northeast-2), 고정 IP `13.124.206.169`
- 코드: `~/Prompick`

---

## 1. 배포

**배포는 서버를 껐다 켜는 일이다.** 그때 제작 중이던 작업은 끊기고, 10분 뒤 다른 워커가
집어서 **처음 단계부터** 다시 돌린다 — 이미 낸 AI 요금을 한 번 더 내는 셈이다.
그래서 순서가 있다.

### 순서

1. 관리자 화면 → **배포 준비**(`/admin/deploy`) → **제작 잠그기**
   - 이 순간부터 새 요청만 막힌다. 돌던 작업은 끝까지 간다.
   - 안내 띠가 모든 화면에 저절로 뜬다. 공지를 따로 쓸 필요 없다.
2. 같은 화면에서 **"지금 배포해도 돼요"**가 뜰 때까지 기다린다
   - 늦어도 20분이면 대기열이 빈다. 화면이 5초마다 알아서 확인한다.
3. 서버에서 배포한다
   ```bash
   cd ~/Prompick
   git pull
   docker compose up -d --build
   ```
4. 올라온 것을 확인하고 **제작 다시 열기**

### 빌드가 오래 걸릴 때

`tmux` 안에서 하면 접속이 끊겨도 살아남는다.

```bash
tmux new -s deploy      # 처음
tmux attach -t deploy   # 다시 붙을 때
```

## 2. 상태 보기

```bash
docker compose ps                 # 세 개가 Up, api 는 healthy 여야 한다
docker compose logs -f api        # 백엔드
docker compose logs -f caddy      # 인증서·접속
free -h                           # 메모리와 스왑
docker stats --no-stream          # 컨테이너별 사용량
```

`api` 가 `Up (unhealthy)` 로 보이면 애플리케이션이 죽은 것이 아니라 **헬스체크가 실패**하는
것이다. `docker compose logs api` 로 `Started PrompickApiApplication` 이 있는지부터 본다.

---

## 3. 메모리

4GB를 이렇게 나눈다.

| | 몫 |
|---|---|
| api (JVM 힙 약 1GB) | 1.5GB |
| web (Next.js) | 0.7GB |
| caddy | 0.128GB |
| OS·도커·빌드 | 나머지 약 1.7GB |

**두 번째 배포부터는** 기존 컨테이너가 돌아가는 채로 빌드가 시작되므로 순간 4GB를 넘길 수
있다. 그래서 스왑 2GB를 잡아 두었다(`/swapfile`). 빌드가 느려질 뿐 죽지는 않는다.

백엔드가 OutOfMemory 로 죽으면 힙 덤프가 `api_dumps` 볼륨에 남는다.

```bash
docker compose exec api ls -la /app/dumps
```

---

## 4. 인증서

Caddy 가 알아서 받고 갱신한다. 만료일을 달력에 적을 필요가 없다.

처음 발급과 갱신 모두 **80번 포트로 도메인 소유를 확인**한다. Lightsail 방화벽에서 80을
닫으면 갱신이 조용히 실패하다가 90일 뒤 사이트가 멈춘다. **80은 닫지 않는다.**

받아온 인증서는 `caddy_data` 볼륨에 있다. 이 볼륨을 지우면 새로 발급받는데, Let's Encrypt
에는 발급 횟수 한도가 있으므로 함부로 지우지 않는다.

## 5. 환경변수

`~/Prompick/.env` 하나다. 저장소에는 값이 빠진 `.env.server.example` 만 있다.

바꾼 뒤에는 다시 올려야 적용된다.

```bash
nano .env
docker compose up -d --build
```

> `NEXT_PUBLIC_*` 값은 **빌드할 때 코드에 글자로 박힌다.** 실행할 때 읽는 것이 아니라서
> 바꾸면 반드시 `--build` 로 다시 만들어야 한다.

> `PROMPICK_MASTER_KEY` 는 한 번 정하면 바꾸지 않는다. 이 값으로 AI 제공사 키를 DB에
> 봉인해 두었기 때문에, 바뀌면 관리자 화면에 넣어 둔 키를 읽지 못한다.

## 6. 되돌리기

```bash
git log --oneline -5
git checkout <되돌아갈 커밋>
docker compose up -d --build
```

DB 마이그레이션이 섞인 배포는 이것만으로 되돌아가지 않는다. Flyway 는 되돌리지 않으므로,
스키마를 바꾼 배포를 되돌릴 때는 되돌리는 마이그레이션을 새로 써서 앞으로 나아간다.

---

## 7. 막혔을 때 보는 곳

| 증상 | 먼저 볼 것 |
|---|---|
| 사이트가 안 뜬다 | `docker compose ps` — 셋 다 Up 인가 |
| https 가 안 된다 | `docker compose logs caddy` — 인증서를 받았나, 80번이 열려 있나 |
| 홈은 뜨는데 내용이 없다 | `docker compose logs api` — DB에 붙었나 |
| 제작이 안 걸린다 | `/admin/deploy` — 잠금을 안 풀었나 |
| 느리다 | `docker stats` — 메모리가 스왑으로 넘어갔나 |

바깥에서 보는 방법:

```bash
curl -s https://yspace.kr/actuator/health     # {"status":"UP"}
curl -s https://yspace.kr/api/v1/service-status
```
